## 实验二：上下文压缩对照

### 要验证什么

比较完整保留搜索结果与按当前任务生成摘要，对工具调用、输入量、耗时和任务完成情况的影响。

### 我的操作

使用 DeepSeek Flash 运行 `no_compression` 和 `context_aware_summary`，每组最多 5 轮。

### 实际结果

| 指标 | 无压缩 | 按任务摘要 |
|---|---:|---:|
| 模型轮数 | 5 | 5 |
| 工具调用 | 17 | 8 |
| 主 Agent token | 54,626 | 30,287 |
| 耗时 | 16.28 秒 | 33.79 秒 |
| 处理后文本长度 | 10,192 字符 | 387 字符 |
| 最终答案 | 无 | 无 |

### 结果分析

- 摘要组输入更短、主 Agent token 更少，但额外摘要调用的 token 没有计入。
- 摘要组耗时更长，可能与额外模型调用有关。
- 两组都达到轮数上限，没有完成任务，因此不能说摘要策略效果更好。
- 两组实际处理的材料和调用路径不同，不能当成固定文本上的严格质量对比。

### 实验结论

压缩是在信息保真、成本和延迟之间做取舍。文本变短只是中间指标，最终仍要看任务能否完成。

## 实验三：KV Cache 固定前缀与变化前缀

### 要验证什么

比较相同材料下，固定前缀和变化前缀对缓存命中的影响。

### 我的操作

两组各请求 3 次：固定组保持长前缀完全一致；变化组在前缀前部加入变化内容。

### 实际结果

| 组别 | 第一次 | 后续请求 |
|---|---:|---:|
| 固定前缀 | 命中 0% | 命中 3200/3393，约 94.3% |
| 变化前缀 | 命中 0% | 仍为 0% |

### 结果分析

缓存依赖从开头连续一致的 token 前缀。用户问题位于后部时可以变化；如果在前部插入动态编号，后面的长材料也难以复用。

### 实验结论

KV Cache 不减少逻辑输入 token 数量，但可以复用已有计算，从而影响费用和首字延迟。实际效果以服务端返回的缓存字段为准。

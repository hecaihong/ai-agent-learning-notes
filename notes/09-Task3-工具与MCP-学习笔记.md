## 项目目的

这一章解决的核心问题是：模型怎样通过工具读取环境、改变环境或与其他参与者协作，以及 Harness 怎样在真实执行前后进行参数校验、权限控制、审批、隔离、验证和轨迹记录。

```text
模型依据任务与 schema 选择工具和参数
  → Harness 校验、授权并执行真实能力
  → 工具结果回到上下文
  → 模型根据新证据继续决策
```

工具可以是 Python 函数、CLI、HTTP API、MCP Server 或人工协作入口。每个 `def` 是函数，不是一个“小模型”。

## 五类工具

| 类型 | 主要作用 | 示例 |
| --- | --- | --- |
| 感知工具 | 获取环境信息 | 搜索、读文件、查数据库 |
| 执行工具 | 改变环境状态 | 写文件、运行代码、业务操作 |
| 协作工具 | 委托其他参与者 | 子 Agent、人工审批、通知 |
| 事件触发 | 环境主动通知 Agent | Webhook、定时任务、消息队列 |
| 用户沟通 | 获取补充信息并反馈 | 表单、聊天、语音 |

## MCP 与 Skill 的关系

MCP Client 通过 `tools/list`、`tools/call`、`resources/read` 等协议与 MCP Server 交互。Server 可以暴露 Tools、Resources 和 Prompts；本地常用 `stdio`，远程常用 Streamable HTTP。

MCP 解决标准通信和能力暴露，Skill 主要分发“如何使用现有能力”的流程知识。是否使用 MCP，以及工具定义是否一次性全部进入上下文，是两个独立决策。协议统一也不代表服务器安全、实现正确或权限合理。

## 工具说明和参数 schema

高质量工具定义至少应说明：何时使用、何时不用、参数类型和单位、返回结构、错误形式、代价与副作用。模型依据这些信息选择工具；Harness 仍需把工具名映射到真实函数，并在边界处验证参数。

Harness 不应暗中改写模型参数。若必须规范化路径、引号或格式，应公开规则、保留原始输入并在结果中说明转换，避免模型看到的调用与实际执行不一致。

## 工具发现与 KV Cache

当工具达到几十或上百个时，每轮发送全部 schema 会增加 token、挤占上下文并提高选错概率。可以只常驻少量核心工具和 `discover_tools`，等模型发现能力缺口后再检索 3—5 个候选工具，将完整 schema 追加到轨迹。

新 schema 追加后应保持位置与内容稳定，以便前面的共同前缀继续复用 KV Cache。修改、移动或重排前缀中的工具定义，通常会让变化点之后的缓存失效。Skills 的渐进式披露也采用类似思路：先看名称和描述，需要时再读取完整说明与脚本。

## 感知工具的输出契约

- 列表结果提供分页、游标和总数；
- 文件读取提供 `offset / limit` 和截断标志；
- 返回来源、时间、权限范围和结构化错误；
- 缓存键包含租户、用户、权限与查询条件，并设置 TTL；
- 网页和工具返回文字是外部证据，不能自动升级成系统指令。

多模态信息可以由模型原生读取、先抽取成文本，或交给专用识别工具。选择标准是信息损失、成本、延迟和可审计性。

## 执行工具的安全闭环

```text
工具调用
  → Schema 与边界校验
  → 风险识别和权限检查
  → 必要时审批
  → 受限环境执行
  → 验证返回值和真实副作用
  → 记录轨迹并回传模型
```

提议者—审核者适合开放式计划和不可逆操作，两个模型需要能力相近但有认知差异；Sidecar 适合对单次结构化行为做快速风险分类，可以使用轻量模型。Sidecar 应只读取 `{tool, arguments, target}` 等必要字段，减少提示注入影响；连续拒绝后需要熔断并请求人工判断。

长输出应截断进入上下文的内容，同时持久化完整结果。Python `venv` 只隔离依赖，不是安全沙盒。高风险场景需要工作区权限控制、容器或 microVM。

可重试操作应具备幂等性，例如使用唯一请求 ID 去重，或先查询目标状态再变更。发邮件、转账、拨号等非幂等操作应采用“预检—确认—执行”，执行失败后不能盲目重试。

## 协作工具

子 Agent 协作至少需要创建/取消、消息传递、状态发现三组原语。交接上下文应标注 `[FROM_USER]`、`[FROM_MAIN_AGENT]` 与 `[TOOL_RESULT]`，同时写清任务、边界、输出格式和终止条件。

同步、异步、流式和多轮协作只是运行方式；能否成功主要取决于上下文是否充分、职责是否清楚、超时如何处理以及谁对最终结果负责。

## 代码走读：execution-tools

第一个建议实验是 `chapter4/execution-tools` 的离线 demo：

- `cli.py::cmd_demo()`：组织七步演示；
- `file_tools.py::FileTools`：限制工作区、写/改文件并做语法校验；
- `execution_tools.py::ExecutionTools`：执行代码和 Shell、处理审批与长输出；
- `multilang_executor.py::LanguageExecutor`：启动语言运行时并处理超时；
- `truncate_and_persist()`：截断进入 Context 的长输出，完整内容另行保存。

实验重点不是观察“代码能否运行”，而是识别工作区、linter、审批、超时、输出持久化和副作用验证分别由哪一层负责。

## 本章解决什么问题

模型每次调用都是无状态的。上下文工程解决的是：每一轮应该让模型看到什么、以什么顺序看到，以及如何在信息质量、长度、费用和缓存之间取舍。

## 我的问题与困惑

### Prompt 和 Context 有什么区别？

Prompt 是人为编写的指令；Context 是模型当前实际收到的全部信息。Prompt 只是 Context 的一部分。

### `role` 有什么作用？

`system`、`user`、`assistant`、`tool` 标记消息来源和用途。它们属于聊天 API 的消息协议，不是自然语言内容中的普通标签。

### API 消息里，哪些内容由 Harness 组织，哪些由大模型生成？

整份请求由 Harness 组装和发送，但里面的内容有不同来源。模型主要生成新的回答，以及工具调用的名称和参数。

|         消息内容          |         内容来源及处理方式         |
| :-------------------: | :-----------------------: |
|       系统规则、工具定义       |    开发者提供，Harness 加入请求     |
|         我的任务          |     我输入，Harness 加入请求      |
|      Skill 目录与正文      |   Harness 或技能加载工具读取后注入    |
| `assistant` 回答、工具调用请求 | 模型生成；Harness 保存，并在后续请求中回传 |
|         工具结果          |  工具实际执行后产生，Harness 写回上下文  |
历史 `assistant` 内容来自模型，但下一轮由 Harness 带回来；图中标为 `user` 的 Skill 目录和正文，也是程序注入的。

### `final_answer` 从哪里来？

模型不再发出工具调用、而是返回终止文本后，Harness 把这段文本记录为最终答案。它是实验程序保存的字段，不是所有模型 API 都固定拥有的字段。

### 工具定义为什么放在请求里？

`tools` 告诉模型可用工具、参数类型和必填项。模型根据工具说明生成结构化 `tool_calls`；Harness 再执行真实函数。

### 历史消息为什么要重复发送？

API 不自动记住上一次请求。Harness 必须重新发送足够的历史，模型才能知道任务进度和工具结果。

### KV Cache 和 Cache Hit 有什么区别和联系？

KV Cache 存的是上下文 token 对应的 K、V 中间计算数据。下一次请求如果前缀一致、缓存可用，就可能复用成功，这叫 Cache Hit。它省的是重复计算，token 仍占上下文，答案仍需重新生成。

### 上下文压缩解决什么问题？

减少低价值历史和长工具输出，同时保留继续决策所需的事实、约束、来源、结果和待办。压缩更短不代表一定更正确。

## 怎么在实践中落地

```text
稳定前缀：系统规则 + 稳定工具定义 + 固定资料
动态区域：当前任务 + 新消息 + 新工具结果
历史治理：保留关键事实，压缩或按需加载低价值内容
```

评估上下文策略时同时查看：任务完成率、关键信息是否丢失、工具重复调用、输入 token、缓存命中和额外压缩成本。

# 第五章：Coding Agent 与通用 Agent 理论笔记

原文：[Coding Agent 与通用 Agent](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter5.md)  
实验：[05-第五章-CodingAgent与通用Agent-实验记录](<05-第五章-CodingAgent与通用Agent-实验记录.md>)

## 本章解决什么问题

怎样把前面学的模型、上下文、记忆和工具，组合成一个能实际完成任务的通用 Agent。

核心思路是 **Coding Agent + 文件工作区**：模型针对任务编写、修改和执行代码；工作区保存资料、代码、中间结果和最终产物。

用之前的营收实验来理解：

| 阶段 | Agent 怎么完成任务 |
|---|---|
| 第四章：工具接入 | 提前写好 `summarize_revenue()`，模型选择工具、填写参数 |
| 第五章：代码生成 | 假设要求“合并几份营收表，再画趋势图”，Agent 读取文件、生成处理代码、运行检查，最后交付表格和图 |

本章主要掌握三件事：

1. **扩展能力**：遇到新需求，可以临时写程序处理，不必为每种需求提前准备专用工具。
2. **形成执行循环**：理解需求 → 读取资料 → 写代码 → 执行 → 根据结果修正。
3. **判断是否完成**：检查实际产物和业务要求是否一致，程序能运行只是其中一步。

刚才的逻辑题实验，只展示了“把题目条件翻译成代码，再执行求解”这一小段。两组都答对，说明这四题直接推理也够用；它不能代表完整的 Coding Agent 工程流程。

**核心理解：Agent 的能力来自模型与执行环境的配合——模型提出办法，程序实际行动，再用结果验证和修正。**

## 我的问题与困惑

### Coding Agent 就是书里的七个工具吗？

七个工具是工具箱。Coding Agent 还包括模型的决策、Harness 的组织与执行，以及根据结果继续处理的循环；工具数量不必恰好是七个。

### 决策、行动、执行和观察分别是什么？

模型决定下一步并提出工具调用，Harness 实际执行，工具输出或报错回到上下文，模型据此继续决策。Coding Agent 主要把这套循环用于代码、文件和命令。

### 文件系统，是文件还是一个专门管理 Agent 的系统？

实际使用时，给 Agent 一个受控读写的文件工作区，用来放资料、代码、中间结果和最终产物。底层文件系统负责存储、目录组织和读写，不必另建专门的 Agent 文件管理系统。

工作区可以为空，也可以预放资料和源码。文件保存下来，不代表模型已经看过；工具读取并送入上下文后，模型才能使用。

### 垂直领域 Agent 和这种通用 Agent 最大的差异是什么？

底层循环相同，差异主要在任务范围、领域知识、业务约束和验收标准。垂直领域 Agent 也可以写代码、使用文件工作区。领域能力要落实到上下文、业务工具、执行约束和结果验证中。

### 理解现有项目和理解用户需求，是同一个过程吗？

理解项目，是查清已有代码、入口、依赖和运行方式；理解需求，是明确这次要解决什么问题、受哪些条件约束、什么结果算完成。两者都需要，读取代码不能替用户决定目标。

## 怎么在实践中落地

### 结合 AFSIM Agent：输入不明确时怎样继续推进？

> 以下是基于本次分享包源码的建议，尚未修改产品代码或验证新流程。

源码里的 Skill 已经要求识别目标、只追问关键缺口，并区分事实、假设和资料缺口。目前主要由模型遵守这些规则；后端尚无专门的需求任务卡和就绪检查。

建议沿用现有 Agent，增加一个需求整理阶段：

```text
读取已有工程与资料
→ 整理任务卡：目标、依据、约束、默认项、缺口、交付物、验收条件
→ 有依据且不改变目标的默认项：标明后继续
→ 影响目标或验收的关键缺口：集中追问
→ 条件齐备后生成、执行，并按任务卡验收
```

模型负责解释需求、提出方案和问题；Harness 负责保存任务卡版本、校验必要字段及执行条件。任务卡应明确哪些来自用户、哪些来自资料、哪些是模型建议；不能把建议自动记成用户确认。

需求可以逐步明确，有把握的部分可以先做。官方资料可以补全“怎么实现”，不能替用户决定“要什么结果”。普通对话结束、等待用户补充和工程验收完成，也要分别表示。

### 我的具体诉求：帮助用户把场景行为说清楚

用户可能只给了红蓝双方的对象或装备，没有给具体行为；也可能只描述了模糊的行为。我希望 Agent 主动给出决策提示，帮助用户逐步明确想要什么，再生成脚本。

建议把这个过程称为“行为需求引导”：

- **没有行为描述**：根据已给信息和查到的案例，提出少量候选，说明各自会呈现什么过程、还需要什么信息。
- **行为描述模糊**：先复述当前理解，再围绕“何时触发 → 做什么 → 何时结束 → 怎样观察结果”补齐关键缺口。
- **已有明确描述**：保留原意，不重复询问，也不擅自扩展任务。

每次先处理最影响后续实现的一两个选择。候选要区分案例依据与待验证建议；用户选择后再写入任务卡，建议本身不等于用户要求。

```text
发现行为缺口 → 查可用能力与案例 → 给选项和说明 → 用户选择或补充 → 更新任务卡 → 生成并验收
```

模型负责理解表达、解释候选和组织问题；Harness 负责保存选择、合并补充回答、维持任务阶段和检查执行条件。第一步可以沿用现有聊天界面展示选项，结构化任务卡与后端检查是后续实现建议。

本段记录的是预期交互效果，尚未实现或运行验证。

## 仍未解决的问题

- 已明确“行为缺失／描述模糊时给引导选项”的目标；待用实际输入验证选项质量、追问次数及能否形成可验收的行为需求。
- 用户补充或修改需求后，任务卡、工程版本和验收记录怎样保持一致？
